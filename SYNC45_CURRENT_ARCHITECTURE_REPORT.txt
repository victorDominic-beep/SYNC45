SYNC45 CURRENT BACKEND ARCHITECTURE REPORT
==========================================

This report describes the current codebase only. It does not propose changes.

1. CURRENT HIGH-LEVEL ARCHITECTURE
==================================

The current backend is an Express/Node application started by src/server.ts. It creates one global Application instance, which wires authentication, organization services, repositories, reconciliation, connectors, and AI.

Current flow:

Frontend
  -> Express routes
  -> JWT authentication
  -> organizationId from JWT/body/path
  -> organization connection lookup
  -> credential decryption
  -> organization-specific connector when usable
  -> global connector fallback when credentials are missing
  -> Paystack + ledger fetch
  -> normalization
  -> matching
  -> discrepancy classification
  -> report generation
  -> JSON report persistence
  -> AI insight generation

The intended organization-specific architecture is partially implemented. Organization credentials can be loaded and used, but global environment-backed connectors remain active and are used as fallbacks.

Reports are persisted to data/reconciliation-reports.json by src/repositories/ReconciliationRepository.ts, not to PostgreSQL.

AI insights are generated by src/ai/services/AIInsightService.ts using the configured Groq provider.


2. AUTHENTICATION
==================

Authentication routes are registered under /api/auth in src/api/routes/auth.routes.ts:

- POST /api/auth/register
- POST /api/auth/login
- POST /api/auth/forgot-password
- POST /api/auth/reset-password
- GET /api/auth/me
- POST /api/auth/google

REGISTRATION

POST /api/auth/register is handled by UserService.register() in src/users/UserService.ts.

Expected payload:

{
  "email": "user@example.com",
  "password": "password",
  "name": "Organization Name",
  "firstName": "First",
  "lastName": "Last"
}

Registration:

1. Normalizes the email.
2. Checks whether the email already exists.
3. Creates an organization through PostgresRepository.createOrganization().
4. Creates an admin user linked to that organization.
5. Hashes the password with bcrypt.
6. Creates a JWT containing:
   - sub
   - email
   - organizationId
   - role

The organization ID is generated by src/repositories/PostgresRepository.ts as:

org-{timestamp}-{random number}

LOGIN

POST /api/auth/login:

1. Finds the user by email.
2. Compares the submitted password with password_hash.
3. Creates a seven-day JWT.
4. Returns the user summary and token.

JWT CREATION AND VERIFICATION

src/shared/utils/Jwt.ts uses:

- JWT_SECRET
- fallback secret: sync45-local-dev-secret-change-me
- expiration: 7d

requireAuth() in src/api/middleware/AuthMiddleware.ts:

- Accepts Authorization: Bearer <token>
- Or x-auth-token
- Verifies the JWT
- Places the decoded payload on req.user

There is no database lookup during JWT verification. The middleware does not verify that the user still exists, is active, or still belongs to the organization in the token.

The Google route accepts submitted identity fields. The current code does not verify a Google access token or ID token.

ORGANIZATION SCOPE

src/api/middleware/OrganizationScopeMiddleware.ts compares:

- Organization ID from req.params.id
- Or req.body.organizationId
- Or req.body.organization

Against req.user.organizationId.

If the IDs differ, it returns 403.

Important current limitations:

- If no organization ID is present in the path/body, the middleware allows the request.
- Query-string organization IDs are not checked.
- GET /api/reconciliation/reports is authenticated but has no organization-scope middleware.
- Its ?organizationId= query can therefore request another organization’s reports.
- GET /api/reconciliation/reports/:id passes the report ID through req.params.id, so the scope middleware compares a report ID to an organization ID. This will normally reject valid report requests.


3. ORGANIZATIONS
=================

Routes are defined in src/api/routes/organization.routes.ts.

Routes:

- POST /api/organizations
- GET /api/organizations
- GET /api/organizations/:id
- PUT /api/organizations/:id
- PATCH /api/organizations/:id/activate
- PATCH /api/organizations/:id/deactivate
- DELETE /api/organizations/:id
- GET /api/organizations/:id/connections
- POST /api/organizations/:id/connections
- POST /api/connections

Controllers are in src/organizations/OrganizationController.ts. Business logic is in src/organizations/OrganizationService.ts.

STORAGE

The PostgreSQL repository creates:

- sync45.organizations
- sync45.users
- sync45.organization_connections

The organization table currently stores:

- id
- name
- email
- timestamps

The following Organization properties are reconstructed in code rather than persisted:

- paymentProvider
- ledgerProvider
- settings
- isActive

The database-backed service always reconstructs organizations as:

paymentProvider: "paystack"
ledgerProvider: "excel"
isActive: true

ACTIVATION AND DEACTIVATION

The database-backed activate() and deactivate() methods only check that the organization exists and return true.

They do not update a database column. The database has no organization active-state column in the current schema.

SCOPE ISSUES

POST /api/organizations and GET /api/organizations require authentication but do not apply organization scope. The current implementation therefore permits any authenticated user to invoke those operations.

EXCEL

There is no organization-specific Excel connection model in src/organizations/Organization.ts.

Excel uses global configuration:

These are read by src/bootstrap/Application.ts and used to create the global ExcelConnector.

CSV is separate. CSV files are uploaded through:

POST /api/reconciliation/upload-csv

The upload is stored temporarily in an in-memory map and later used by CSVConnector.

ENCRYPTION

src/organizations/OrganizationService.ts implements AES-256-CBC encryption.

The key is derived from:

CONNECTION_ENCRYPTION_KEY

with a local fallback value.

Encrypted values are represented as:

iv-hex:ciphertext-hex

resolveConnectionConfig() decrypts:

- Paystack secret keys
- MongoDB URIs
- PostgreSQL passwords
- MySQL passwords

IMPORTANT STORAGE MISMATCH

OrganizationService.saveConnections() creates encrypted fields, but it also preserves the original plaintext fields.

Then PostgresRepository.saveConnections() uses expressions such as:

payload.paystack.secretKey || payload.paystack.encryptedSecretKey

Therefore, if plaintext was submitted, the plaintext value is selected for database storage before the encrypted value.

The same applies to:

- MongoDB URI
- PostgreSQL password
- MySQL password

So the code contains encryption and decryption logic, but the database persistence path currently may store plaintext credentials.

SAFE RESPONSES

GET /api/organizations/:id/connections returns masked connection metadata:

{
  "paystack": {
    "connected": true
  },
  "mongodb": {
    "connected": true,
    "database": "...",
    "collection": "..."
  }
}

It does not return secrets.

However, the save response has a separate issue: the database-backed saveConnections() calls findById(), and findById() does not load connection data. Therefore, the save response may omit the saved connection object.


5. CREDENTIAL RESOLUTION DURING RECONCILIATION
==============================================

Route:

POST /api/reconciliation/reconcile

Defined in src/api/routes/reconciliation.routes.ts.

A. WHERE DOES THE ORGANIZATION ID COME FROM?

The request body must contain:

{
  "organizationId": "org-id",
  "from": "2026-01-01",
  "to": "2026-01-31"
}

ReconciliationController.reconcile() reads organizationId from req.body.

The validator and controller require it.

B. HOW IS THE AUTHENTICATED USER'S ORGANIZATION VERIFIED?

The route runs:

1. requireAuth
2. requireOrganizationScope
3. ReconciliationValidator.validate

requireOrganizationScope compares:

req.body.organizationId

with:

req.user.organizationId

This confirms that the request body organization ID matches the organization ID embedded in the JWT.

It does not independently load the user from PostgreSQL or verify that the organization still exists or is active.

C. WHERE ARE CONNECTION SETTINGS LOADED?

ReconciliationService.reconcile() calls:

organizationService.resolveConnectionConfig(request.organizationId)

This is in src/reconciliation/services/ReconciliationService.ts.

The organization service reads the connection row through:

PostgresRepository.getConnections()

D. WHERE ARE ENCRYPTED CREDENTIALS DECRYPTED?

OrganizationService.resolveConnectionConfig() calls its private decrypt() method for:

- row.paystack_secret_key
- row.mongodb_uri
- row.postgresql_password
- row.mysql_password

If a stored value does not contain a colon, decrypt() returns it unchanged. This means plaintext-stored credentials still work as plaintext.

E. WHERE IS THE PAYSTACK CONNECTOR CREATED?

At application startup, a global Paystack connector is created in src/bootstrap/Application.ts:

new PaystackConnector(ConnectorConfig.PAYSTACK_SECRET_KEY)

During reconciliation, if the organization has a resolved Paystack secret, another connector is created in src/reconciliation/services/ReconciliationService.ts:

new PaystackConnector(savedConnections.paystack.secretKey)

F. WHERE IS THE LEDGER CONNECTOR CREATED?

Global connector creation happens in src/bootstrap/Application.ts, based on LEDGER_SOURCE.

During reconciliation, organization-specific connectors are created in src/reconciliation/services/ReconciliationService.ts:

- MongoDB: new MongoDBConnector(...)
- PostgreSQL: new PostgreSQLConnector(...)
- MySQL: new MySQLConnector(...)

CSV creates a temporary CSVConnector.

There is no organization-specific Excel connector creation.

G. ARE ORGANIZATION CONNECTORS USING STORED CREDENTIALS?

Yes, when usable stored credentials exist.

Examples:

- Paystack uses the resolved organization secret.
- MongoDB uses the resolved organization URI/database/collection.
- PostgreSQL uses the resolved organization host/port/database/user/password/table.
- MySQL uses the resolved organization host/port/database/user/password/table.

H. ARE GLOBAL ENVIRONMENT CREDENTIALS STILL USED?

Yes.

The global connectors are constructed at startup from environment-backed configuration. They remain the initial active connectors.

If organization-specific credentials are incomplete, the service does not reject the request. It retains the global connector.

Examples:

- Missing organization Paystack secret: global Paystack connector remains active.
- Missing organization MongoDB URI: global ledger connector remains active.
- Missing organization PostgreSQL password: global ledger connector remains active.
- Missing organization MySQL password: global ledger connector remains active.
- No ledgerSource in the request: global LEDGER_SOURCE determines the default connector.

Therefore, the current behavior is:

organization credentials first, global environment credentials as fallback

It is not organization-only.

I. EXACT RECONCILIATION SEQUENCE

Inside src/reconciliation/services/ReconciliationService.ts:

1. Determine requested ledger source:
   - request ledgerSource
   - otherwise global LEDGER_SOURCE
2. Resolve the organization's stored connection configuration.
3. Replace the global Paystack connector if an organization Paystack secret exists.
4. Replace the global ledger connector if the requested source has usable organization credentials.
5. For CSV, create a temporary CSV connector.
6. Connect to the active ledger connector.
7. Fetch Paystack transactions.
8. Fetch ledger transactions.
9. Normalize both transaction sets.
10. Match transactions with TransactionMatcher.
11. Classify discrepancies.
12. Generate the report.
13. Generate AI insights.
14. Persist the report to JSON.
15. Disconnect the active ledger connector.

7. POSTGRESQL INFRASTRUCTURE
============================

There are two distinct PostgreSQL roles.

SYNC45 INTERNAL POSTGRESQL

Used by src/repositories/PostgresRepository.ts for:

- organizations
- users
- organization connections

Configured through src/config/PostgreSQLConfig.ts:

- POSTGRESQL_HOST or POSTGRES_HOST
- POSTGRESQL_PORT or POSTGRES_PORT
- POSTGRESQL_DATABASE or POSTGRES_DB
- POSTGRESQL_USER or POSTGRES_USER
- POSTGRESQL_PASSWORD or POSTGRES_PASSWORD
- POSTGRESQL_SSL
- PGSSLMODE
- POSTGRESQL_SSL_REJECT_UNAUTHORIZED

Default database values include:

- database: sync45_test
- user: postgres
- password: admin

ORGANIZATION LEDGER POSTGRESQL

Used by src/connectors/ledger/postgresql/PostgreSQLConnector.ts to read an organization's external ledger transactions.

Its credentials are intended to come from the organization connection record:

- host
- port
- database
- user
- password
- table

If those credentials are incomplete, the current service falls back to the global ledger PostgreSQL configuration in src/config/ConnectorConfig.ts.

The same environment variable names are therefore used by the current code for both:

1. Sync45's internal database.
2. The global fallback ledger database.

That creates an architectural collision between internal storage configuration and legacy global ledger configuration.


8. MIGRATION
============

scripts/migrate-pg.js:

- Loads dotenv.
- Creates a pg.Pool.
- Uses POSTGRESQL_* / POSTGRES_* environment aliases.
- Defaults to:
  - host localhost
  - port 5432
  - database sync45_test
  - user postgres
  - password admin

It creates:

- sync45.organizations
- sync45.users
- sync45.organization_connections

It is intended for Sync45's internal PostgreSQL database. It does not create organization ledger tables.

SSL BEHAVIOR

The migration script always sets:

ssl: {
  rejectUnauthorized: false
}

The runtime repository uses conditional SSL from src/config/PostgreSQLConfig.ts:

- SSL is disabled unless POSTGRESQL_SSL or PGSSLMODE enables it.
- rejectUnauthorized is controlled separately.

Therefore, the migration script is not fully consistent with the runtime repository's SSL configuration.


9. HEALTH CHECK
===============

Implementation: src/app.ts

Route:

GET /health

It executes in parallel:

application.paystackConnector.testConnection()
application.ledgerConnector.healthCheck()

These are the global startup connectors from src/bootstrap/Application.ts.

It does not:

- authenticate the request
- identify an organization
- load organization connections
- decrypt organization credentials
- check the internal Sync45 PostgreSQL repository
- check organization-specific connectors

MEANING OF "paystack": false

PaystackConnector.testConnection() returns false when its request fails.

The connector uses the global PAYSTACK_SECRET_KEY, not an organization secret.

MEANING OF "ledger": false

application.ledgerConnector.healthCheck() returns false when the globally selected ledger connector fails.

The connector and credentials depend on global LEDGER_SOURCE and its corresponding environment variables.

WHY IT CAN TAKE APPROXIMATELY 30 SECONDS

The Paystack connector configures Axios with:

 timeout: 30000

If Paystack is unreachable or the global Paystack credentials cause a request that does not complete, testConnection() waits approximately 30 seconds, catches the failure, and returns false.

The route then returns:

503
{
  "success": false,
  "status": "degraded",
  "connectors": {
    "paystack": false,
    "ledger": ...
  }
}

The ledger connectors do not define equivalent explicit query/connect timeouts. They may therefore take longer depending on the database driver and network conditions.

ConnectorConfig.REQUEST_TIMEOUT exists but is not used by these connectors.

12. FINAL VERDICT
=================

A. CURRENTLY CORRECT

- JWTs contain an organization ID.
- Reconciliation requires an organization ID.
- Reconciliation compares the request organization ID with the JWT organization ID.
- Organization connection routes exist.
- Paystack, MongoDB, PostgreSQL, and MySQL connection fields are modeled.
- Credential encryption and decryption helpers exist.
- Organization-specific connector construction exists for Paystack, MongoDB, PostgreSQL, and MySQL.
- Organization credentials take precedence when the required credential is present.
- Connection GET responses mask secret values.
- Internal organizations, users, and connection records are stored in PostgreSQL.
- Reconciliation performs normalization, matching, classification, report generation, persistence, and AI insight generation.

B. STILL USING THE OLD ARCHITECTURE

- Global Paystack connector is created from PAYSTACK_SECRET_KEY.
- Global ledger connectors are created from Render environment variables.
- Missing organization credentials silently fall back to global connectors.
- LEDGER_SOURCE remains a global default.
- /health checks global Paystack and ledger connectors without organization context.
- Excel is entirely global through environment variables.
- Organization connection persistence prioritizes submitted plaintext values over encrypted values.
- Internal PostgreSQL and global PostgreSQL ledger settings share environment variable names.
- Reports are stored in a local JSON file rather than organization-scoped PostgreSQL storage.
- Organization activation/deactivation is not persisted.
- Organization list and report-list routes do not fully enforce organization scope.

C. UNKNOWN / NEEDS VERIFICATION

- Whether the current production database contains plaintext or encrypted connection values.
- Whether Render currently defines the legacy global connector variables.
- Whether the frontend always sends organizationId in reconciliation requests.
- Whether all organizations have complete credentials for their selected connector.
- Whether the internal PostgreSQL database and an organization's ledger PostgreSQL database currently use different physical databases.
- Whether the intended frontend supports Excel as an organization-specific source.
- Whether the 30-second health behavior is currently caused by Paystack, the selected ledger driver, or both in the deployed environment.

FINAL CONCLUSION

The current code implements organization-aware credential resolution, but it has not fully eliminated the old global environment-variable architecture. Organization-specific credentials are optional overrides, while global Render-backed connectors remain the fallback and the health-check implementation.
